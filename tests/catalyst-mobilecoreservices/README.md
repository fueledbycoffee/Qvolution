# Catalyst MobileCoreServices boundary

Stage33 reports an unresolved load at `/System/iOSSupport/System/Library/Frameworks/MobileCoreServices.framework/Versions/A/MobileCoreServices`. This is the entire observed app-specific premise; no binary internals or app symbol list were inspected. The candidate creates that install identity and reexports the existing LaunchServices subframework. It does not claim complete MobileCoreServices ABI compatibility or change UTI semantics.

Public API provenance: Apple's [UTI adoption guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/understanding_utis/understand_utis.tasks/understand_utis_tasks.html) identifies MobileCoreServices UTI constants and utility functions; [UTTypeCreatePreferredIdentifierForTag](https://developer.apple.com/documentation/coreservices/1448939-uttypecreatepreferredidentifierf?language=objc) documents typed parameters, Create ownership and the possibility of multiple results. In our source, CoreServices reexports LaunchServices, and LaunchServices `UTType.m` and `constants.c` implement the tested functions and constants. The existing `IOSSUPPORT` framework helper gives the candidate its Catalyst install name and versioned layout; the existing `reexport` helper emits ld64's reexport flag.

Run `cmake -P tests/catalyst-mobilecoreservices/cmake-contract.cmake` on the host for a narrow structural check. It mocks framework creation and does not compile, inspect a Mach-O, or establish runtime behavior.

For a separately authorized build/staged guest validation, build and install the target with the usual project tooling, confirm the file and symlinks and inspect its Mach-O install name and reexport load command. Compile `uti-reexport.c` as a guest C executable against CoreFoundation and libSystem (no direct LaunchServices dependency), then run it with the staged install. It uses the exact Catalyst path and typed lookups through that handle and exercises case-insensitive equality and a registered PNG lookup. The PNG assertion assumes a clean LaunchServices database containing the existing CoreServices PNG declaration and no competing preferred PNG declaration; Apple leaves selection unspecified when several match. Verify that precondition independently. A further client linked against the framework and the original app launch remain root-owned integration checks.

Existing limitations remain: LaunchServices' identifier lookup depends on its registration database; its unknown-extension dynamic identifier is explicitly a placeholder, and conformance/dynamic behavior is incomplete. The fixture does not endorse those limitations as the platform contract. Mach-O reexport and guest execution are unverified here. This wrapper reexports all existing LaunchServices symbols, a broader surface than the documented UTI subset, and its version numbers are project defaults, not verified platform ABI metadata. Check loader compatibility and version requirements before merging.
